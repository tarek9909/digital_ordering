# Authentication, authorization, tenancy, and realtime source review

Reviewed 2026-10-22. This is a read-only defensive review of the current source, including the audit-repair changes. Findings below are **source-confirmed**, not runtime-confirmed. No authentication bypass scripts, live-provider requests, production edits, or shared application-data mutations were performed for this review. Suggested tests describe the behavior a repair should require; they have not been executed here.

Reviewed the API route registry and authorization middleware; tenant/user/platform authentication; password, invitation, MFA, OAuth and handoff services; staff and display credentials; support sessions; tenant scoping; integration-key resolution; and realtime authentication/fanout. Customer push/claim workflows, infrastructure and browser rendering are covered separately by the main audit.

## Findings

### AUTH-01 — Existing-account invitation acceptance omits enrolled MFA

**Severity: High. Confidence: source-confirmed.**

**Preconditions:** A valid, unexpired invitation for an existing password account, and that account's correct password. The account has an enrolled authenticator. Possession of the invitation alone is insufficient.

**Missing check:** [auth.ts:368](../../../backend/packages/services/src/auth.ts#L368) selects only the existing user's ID/password hash and verifies the password. It neither selects nor checks `totp_secret_enc` or `disabled_at`. After changing the membership, [auth.ts:390](../../../backend/packages/services/src/auth.ts#L390) calls `createUserSession(..., false)` unconditionally. The acceptance route [routes/auth.ts:203](../../../backend/apps/api/src/routes/auth.ts#L203) then sets the resulting session cookie. In contrast, ordinary password sign-in [auth.ts:71](../../../backend/packages/services/src/auth.ts#L71) challenges enrolled MFA, and Google sign-in now does so too.

**Impact:** The invitation login path has a weaker authentication requirement than the same account's normal login. For a single-venue tenant, the session has the invited manager/owner's ordinary permissions without its enrolled second factor. Multi-venue HTTP management has an additional MFA gate, so that particular gate limits the immediate scope there. This also fails to reject a disabled existing account.

**Recommended fix:** Apply account status and authentication policy to every session-issuing path. Existing users accepting invitations should complete their enrolled MFA before an authenticated tenant session is issued. Keep invitation/membership acceptance state consistent across retries and failed MFA.

**Safe regression requirements:** With a disposable existing user enrolled in TOTP, invitation acceptance with the correct password must return an MFA challenge and no full session. Incorrect/missing MFA must not grant API access. Cover no-MFA new users, existing Google-only users, disabled users, expired/revoked invitations, and both single/multi-venue tenants.

### AUTH-02 — A session alone can replace or remove an existing authenticator

**Severity: High for persistence after session compromise. Confidence: source-confirmed.**

**Preconditions:** A usable authenticated tenant-user session and its CSRF token, or access to an unlocked signed-in browser. This finding does not assert that an anonymous caller can change MFA.

**Missing check:** The three MFA-management routes [routes/auth.ts:251](../../../backend/apps/api/src/routes/auth.ts#L251) through line 275 require only `account.self` and normal session CSRF. [auth.ts:247](../../../backend/packages/services/src/auth.ts#L247) creates a new pending secret without checking whether MFA already exists. [auth.ts:254](../../../backend/packages/services/src/auth.ts#L254) verifies only a code generated by that *new* secret, then overwrites the enrolled secret. [auth.ts:264](../../../backend/packages/services/src/auth.ts#L264) removes MFA without a password, old-factor code, recent-authentication requirement, recovery challenge, or account-policy check.

**Impact:** Temporary access to a signed-in session is enough to alter the account's future authentication policy. An enrolled second factor provides no additional protection for its own replacement/removal. This is an account-security persistence issue; baseline session compromise is an explicit prerequisite.

**Recommended fix:** Separate first-time enrollment from replacement/removal. Require recent step-up verification using an already enrolled factor or a deliberately designed recovery mechanism for replacement/removal. Require an appropriate first-factor check when enrolling from an existing session. Record and notify security-sensitive factor changes, rotate session assurance, and revoke dependent/pending authentication artifacts.

**Safe regression requirements:** An ordinary or stale session must not replace/remove an enrolled factor without fresh verification of the existing factor. A code for a newly proposed factor must prove enrollment only, not authorize replacement of an existing one. Test legitimate recovery explicitly.

### AUTH-03 — MFA removal retains the current session's verified assurance

**Severity: Medium. Confidence: source-confirmed.**

**Preconditions:** An existing MFA-verified user session, including in a tenant with multiple active venues.

**Missing check:** [auth.ts:264](../../../backend/packages/services/src/auth.ts#L264) clears the user's authenticator but keeps the calling session and its `mfa_verified_at`. [auth.ts:143](../../../backend/packages/services/src/auth.ts#L143) turns that timestamp into `mfaVerified: true` without checking current enrollment. The mandatory multi-venue HTTP gate [router.ts:122](../../../backend/apps/api/src/http/router.ts#L122) trusts that boolean. The delete-MFA route has no mandatory-MFA-policy check.

**Impact:** A current session can continue satisfying mandatory multi-venue MFA after its account has removed its only factor. The current-session exception to revocation retains that state until the session is revoked/expires. This is distinct from the missing reauthentication in AUTH-02: it also affects an authorized user deliberately removing their own factor.

**Recommended fix:** Enforce tenant/account MFA policy during removal. Where removal is allowed, clear assurance on every session and require fresh enrollment/authentication before protected management resumes. Evaluate the present enrollment/assurance version as part of the policy gate.

**Safe regression requirements:** Removing the sole factor in a mandatory-MFA context is either rejected or immediately blocks protected operations on all sessions, including the calling session. Preserve access only to intentional enrollment/recovery/account routes.

### AUTH-04 — User-session revocation does not evict existing staff-board sockets

**Severity: High for continued data access after revocation. Confidence: source-confirmed.**

**Preconditions:** A legitimately authenticated owner/manager staff-board websocket is already connected. The user then signs out, resets/changes credentials, loses membership, or has their session revoked.

**Missing check:** [realtime/server.ts:64](../../../backend/apps/realtime/src/server.ts#L64) authenticates only at handshake. Its user branch [server.ts:87](../../../backend/apps/realtime/src/server.ts#L87) joins venue/tenant rooms but does not retain the user ID/session ID in `SocketData`, join a session room, periodically revalidate authorization, or register a revocation path. Fanout [server.ts:178](../../../backend/apps/realtime/src/server.ts#L178) sends staff projections directly to those rooms. [team.ts:43](../../../backend/packages/services/src/team.ts#L43) and session-revocation helpers update database state without disconnecting these user sockets. Device/display revocation has explicit disconnect events, highlighting the missing equivalent for user sessions.

**Impact:** A previously authorized connected client can keep receiving new staff ticket projections after HTTP access has been withdrawn. Those projections contain ticket bearer tokens, internal notes/references, claim/check codes and operational details ([projections.ts:91](../../../backend/packages/services/src/projections.ts#L91)). This is continued read/event access, not an assertion that websocket clients can invoke HTTP ticket mutations after revocation.

**Recommended fix:** Associate sockets with authoritative user/session identity and propagate session, membership, role and security-state changes to all realtime instances. Disconnect or remove unauthorized room memberships on revocation, and periodically revalidate as a fallback. Ensure expiration applies to already established sockets.

**Safe regression requirements:** With a disposable signed-in board connection, revoke its session/remove its membership using normal service methods. The connection must lose access before subsequent synthetic staff events are delivered. Cover logout, password reset, factor replacement, role changes, absolute/idle expiry, and multiple realtime instances. Preserve working device/display revocation behavior.

### AUTH-05 — Realtime owner/manager access omits the mandatory multi-venue MFA gate

**Severity: Medium. Confidence: source-confirmed.**

**Preconditions:** A password-authenticated owner/manager session with `mfaVerified: false` for a tenant with multiple active venues. This is a normal possible state before first-time MFA enrollment; it does not require a forged session.

**Missing check:** The HTTP staff/admin registry applies `mfaRequiredFor(...)` in [router.ts:122](../../../backend/apps/api/src/http/router.ts#L122). The matching realtime user branch [server.ts:90](../../../backend/apps/realtime/src/server.ts#L90) checks only session and active membership, then joins staff/tenant rooms. It never checks the session's MFA assurance or multi-venue policy.

**Impact:** A session that is intentionally blocked from HTTP board/management access pending mandatory MFA can still subscribe to staff-board data and event streams. Scope is the authenticated membership and a venue within that tenant; source shows the venue query is tenant-scoped.

**Recommended fix:** Reuse one effective access-policy evaluator for both HTTP and realtime, including MFA, current tenant state, venue state and user/session lifecycle. Keep the minimal enrollment path available without granting protected rooms.

**Safe regression requirements:** A no-MFA multi-venue session must be denied protected staff-room admission; a correctly MFA-verified session must work. Test the transition from one to multiple active venues while an existing socket is connected.

### AUTH-06 — Disabling a platform agent leaves their issued support credentials usable

**Severity: High. Confidence: source-confirmed.**

**Preconditions:** A platform agent already holds a tenant support cookie from a legitimately approved/emergency support session. A super admin subsequently disables the agent, removes their support role, or resets MFA to contain suspected compromise.

**Missing check:** [console.ts:214](../../../backend/packages/services/src/console.ts#L214) disables the platform account and revokes only `platform_sessions`. [console.ts:225](../../../backend/packages/services/src/console.ts#L225) resets MFA and similarly revokes only console sessions. Neither terminates active `support_sessions` or invalidates their handoffs/tokens. [support.ts:186](../../../backend/packages/services/src/support.ts#L186) joins the platform user solely for the agent name; it checks tenant/session expiry but never `platform_users.status`, the current allowed role, or an authentication/security version.

**Impact:** The retained support cookie can continue authorized support operations until that support session is ended/expires, even though the platform account's console access was withdrawn. The support permission set includes ticket writes, venue settings and staff-access management ([permissions.ts:57](../../../backend/packages/auth/src/permissions.ts#L57)). Existing restrictions on billing management, API-key creation, ownership, exports and tenant deletion still apply.

**Recommended fix:** End/invalidate every derived support credential when its parent account is disabled, loses the relevant role, or undergoes a security-reset event. Resolve support actors against current account status and an assurance/security version. Revoke outstanding support handoffs too.

**Safe regression requirements:** Approve a disposable support session and verify ordinary access; disable the agent via the supported service and require immediate rejection of the existing tenant support cookie and pending handoff. Repeat for MFA reset/role removal, while testing explicit tenant ending/expiry still work.

### AUTH-07 — OAuth state is not bound to the browser that initiated login

**Severity: Medium (login CSRF/account confusion). Confidence: source-confirmed; live-provider acceptance unverified.**

**Preconditions:** Google sign-in is configured and a user is directed to a valid pending callback initiated outside that user's browser context. This finding does not assert theft of a victim's Google account or arbitrary account takeover.

**Missing check:** [account.ts:121](../../../backend/packages/services/src/account.ts#L121) stores state/nonce/PKCE verifier and a return host only. [account.ts:130](../../../backend/packages/services/src/account.ts#L130) locates this record solely by the callback's `state`. Neither the service nor [routes/auth-r11.ts:28](../../../backend/apps/api/src/routes/auth-r11.ts#L28) issues/checks an initiating-browser cookie or other browser-bound transaction secret. Callback processing sets the www session cookie for the verified provider identity on whichever browser receives that callback.

**Impact:** State/nonce/PKCE authenticate the authorization transaction, but the application does not associate that transaction with the initiating browser. The remaining source-level risk is a victim receiving a session for an unexpected account (login CSRF/account confusion). Enrolled application MFA is now correctly required for provider identities that have it.

**Recommended fix:** Bind the OAuth transaction to a short-lived, secure, host-only, HttpOnly browser cookie or an equivalent server session, and require that binding in addition to provider state/nonce/PKCE checks. Use an atomic single-use consume and clear it after completion.

**Safe regression requirements:** A callback for a transaction initiated in browser/session A must be rejected in browser/session B even when the provider returns valid claims. The same-browser callback must succeed once; missing/wrong/expired cookie, reused state and incorrect nonce/verifier must fail.

### AUTH-08 — Configured console IP allow-list is never enforced

**Severity: Medium when configured. Confidence: source-confirmed.**

**Preconditions:** An operator sets a nonempty `console.ipAllowList`, expecting to restrict console access to approved source addresses. An empty/default list intentionally imposes no restriction.

**Missing check:** The requirement is explicit: [Technical-Requirements-Document.md:1917](../../../Technical-Requirements-Document.md#L1917), TR-SEC-12, specifies the optional console IP allow-list through this platform setting. The setting exists in [settings.ts:147](../../../backend/packages/contracts/src/settings.ts#L147), is returned by [console.ts:240](../../../backend/packages/services/src/console.ts#L240), can be edited/saved by the generic console settings UI [Settings.tsx:31](../../../frontend/apps/web-console/src/pages/Settings.tsx#L31), and is persisted by `putSetting`. Repository search found no policy consumer for this setting. The API console-context branch [middleware.ts:122](../../../backend/apps/api/src/http/middleware.ts#L122) resolves console cookies without an IP policy. The console host block [Caddyfile:90](../../../deploy/Caddyfile#L90) proxies/serves the console without a corresponding restriction.

**Impact:** Saving a populated security setting gives the operator false assurance: sources outside it still reach the normal console login/API authorization boundary. Password/MFA/RBAC still apply; this finding does not imply anonymous console authentication. The advertised extra network restriction is absent.

**Recommended fix:** Validate addresses/CIDRs, implement enforcement at a trusted source-IP boundary for console login/callback and authenticated API traffic, document any intentionally exempt paths, and provide an effective-policy status. Keep an explicit recovery mechanism for accidental operator lockout. If this feature is deferred, remove its editable appearance or label it as unavailable until enforcement exists.

**Safe regression requirements:** With a disposable nonempty allow-list, requests from outside it must fail at login and authenticated console APIs, including existing sessions. Allowed IPv4/IPv6/CIDR cases must work, malformed rules must be rejected, forwarding headers must not let an untrusted client choose its evaluated address, and empty-list behavior must be explicit.

## Additional hardening and test gaps

- `resolveUserSession` ([auth.ts:134](../../../backend/packages/services/src/auth.ts#L134)) does not consult `users.disabled_at`; the MFA-completion path also omits it. No general tenant-user disable endpoint was identified in this pass, so this is recorded as a lifecycle hardening gap rather than claiming an exposed disable-flow vulnerability. Make account-disabled policy consistent at all resolvers/session issuers.
- TOTP login has an existing per-IP route limit of 30/15 minutes ([routes/auth.ts:46](../../../backend/apps/api/src/routes/auth.ts#L46)). Failed MFA calls increment service counters but do not consult `checkThrottle`, consume an attempt budget on the challenge, or prevent accepted-step code reuse. Factor-management and `/mfa/refresh` have no explicit route attempt limit. Add challenge/account/device budgets and accepted-step replay protection; do not describe the existing login path as completely unthrottled.
- One-use handoff, MFA, OAuth and support records commonly use separate KV `get` and `del` operations. Use atomic consumption and transaction-safe invitation/email-token redemption. This source pattern is an opportunity to strengthen replay/concurrency handling; concurrent exploitation was not tested.
- Console fresh-MFA enforcement is present on selected destructive routes but is not applied to platform-user invitation/role mutation. Require a consistent step-up policy for privilege grants as well as MFA reset/deletion.
- Realtime handshake/client tracking maps are never pruned after expiration or disconnection; event handlers have no general message-rate budget. Bound/prune maps and enforce per-connection event budgets, particularly for log-producing events. Resource-exhaustion impact was not load-tested.

## Controls observed working by construction in the reviewed source

- Every route mounted through the shared registry declares a permission/surface, executes `authorize`, validates declared inputs and normally enforces CSRF for cookie-authenticated mutations ([router.ts:97](../../../backend/apps/api/src/http/router.ts#L97)). Public/session-establishment exemptions require separate consideration.
- User sessions are random bearer tokens stored as keyed hashes, bound to their issuing host, and checked for revocation/absolute/idle lifetime. Tenant middleware rechecks active membership and derives role from the database on each HTTP request ([middleware.ts:101](../../../backend/apps/api/src/http/middleware.ts#L101)).
- Production cookie options set HttpOnly, Secure, SameSite=Lax, host-only scope and Path=/ ([router.ts:169](../../../backend/apps/api/src/http/router.ts#L169)). Insecure names are explicitly controlled by configuration.
- The tenant query plugin appends tenant constraints to tenant tables/joins, parenthesizes preexisting OR filters, rejects foreign/missing tenant IDs on inserts and rejects unsafe raw tenant-table queries ([tenant-scope.ts:89](../../../backend/packages/db/src/tenant-scope.ts#L89)). This review did not identify a concrete HTTP tenant-isolation escape in those controls; this is not proof that every future raw/platform query is scoped correctly.
- Staff/display credentials presented to the HTTP API on another tenant host fail tenant matching. Staff ticket mutations additionally constrain the venue rather than trusting a supplied foreign venue ID.
- Support RBAC explicitly denies billing changes, integration management, ownership, tenant deletion/export and approval of additional support access ([permissions.ts:57](../../../backend/packages/auth/src/permissions.ts#L57)). Explicitly ending/expiring a support session is checked by its resolver.
- Google sign-in now requires enrolled TOTP and rejects disabled accounts; tenant handoff carries completed MFA assurance and verifies host, tenant and user agent. The previous functional-audit Google-MFA/handoff findings should not be repeated as current defects.
- API-key resolution now checks current API entitlement and key limits on each request ([integration.ts:48](../../../backend/packages/services/src/integration.ts#L48)); retained database keys alone do not demonstrate downgrade access.
- Staff-device and display revocation have explicit realtime disconnection events. Named-staff token resolution now rechecks current active status rather than blindly renewing an inactive staff member's token.

Existing tests cover nominal invitation acceptance, support approval/end/expiry, RBAC, cookie CSRF, cross-tenant HTTP resources and selected realtime tenant isolation. The source-confirmed lifecycle/policy cases above require additional regression coverage. No claim of complete exploitability, live-provider validation, load resistance or security certification is made by this source-only pass.
